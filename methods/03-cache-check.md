# 03 缓存命中检测

目标：确认两件事——① 缓存真的开启了；② 命中后计费真的降了。只有①没有②，等于没省钱，同样是掺水（缓存返还被中转吃掉）。

## 原理（一分钟版）

长 prompt 第一次发过去，服务端会把它缓存起来（这一次通常有 cache_creation 计费，略贵）；短时间内发**完全相同**的长 prompt，服务端直接读缓存（cache_read / cached_tokens），这部分按远低于正常输入的价格计费。长会话、长文档、Claude Code 这类反复带同一上下文的场景，缓存是成本大头。

## 手工步骤

1. 准备一段长文本做 prompt：建议 ≥2000 token（太短有些服务不触发缓存）。可用自己的项目文档。
2. **连发两次，内容一字不差**，间隔控制在 1 分钟内（缓存有有效期，常见为分钟级，拖太久测的是过期不是未开启）。
3. 去控制台逐条用量看第二次请求：
   - cached / cache_read 字段 **> 0** → 缓存开启
   - 第二次实际费用比第一次明显下降（量级参考：命中部分单价通常只有正常输入的约 1/10，各家口径不同，看「明显下降」即可）→ 返还正常
4. 换一个时段再测一组，排除单次偶发。

## 脚本步骤（OpenAI 兼容接口）

```bash
export RELAY_BASE_URL="https://你的接入地址"   # 占位示例，填你自己的
export RELAY_API_KEY="sk-xxxx"                  # 占位示例，只走环境变量
export RELAY_MODEL="your-model-name"            # 你要测的模型名
./scripts/cache_probe.sh
# 也可以自备长文本: ./scripts/cache_probe.sh --file my-long-prompt.txt
```

脚本会连发两次同一请求并打印两次的 usage 字段（prompt_tokens / cached_tokens 等）供你判读。密钥只从环境变量读，脚本内没有、也不会打印密钥。

注意接口差异：Anthropic 原生接口的缓存字段叫 `cache_creation_input_tokens` / `cache_read_input_tokens`，且需要请求里带 cache_control 标记才触发；OpenAI 兼容层通常自动缓存并在 usage 里给 `prompt_tokens_details.cached_tokens`。你用的站走哪种口径，就看哪个字段——判读逻辑一致：**第二次要出现非零的缓存读取数**。

## 判读表

| 现象 | 判读 |
|---|---|
| 第二次 cached >0，费用明显降 | 通过 |
| 第二次 cached >0，但费用几乎没降 | 黄旗偏红：缓存开了但返还被吃，问口径，无合理解释按红旗 |
| 偶发一次 cached = 0 | 黄旗：换时段复测两次再判 |
| 多个时段、多次连发恒为 0 | **红旗**：没开缓存或不返还，长会话别在这家跑 |
| 控制台根本不展示缓存字段 | 黄旗起步：关键计费字段不可见，本身就是透明度问题 |

## 注意事项

- 两次请求必须**完全一致**：多一个空格、时间戳变量、随机 ID 都会让前缀对不上而不命中——测试时关掉你客户端里会自动注入变量的部分，用裸请求测最干净。
- 缓存通常按 prompt **前缀**匹配：长文本放前面、变化的问题放后面，命中率才高。这也是日常使用里省钱的正确姿势，不只是测试技巧。
- 第一次略贵是 cache_creation 的正常成本，别把第一次的高价误判为多扣；对账方法见 methods/02。

## 自测通过标准

- 至少两个时段各测一组连发，第二次缓存字段与费用都记了具体数字
- 结论落到「通过 / 开了不返还 / 长期零命中」三者之一
