# 02 Token 对账

目标：搞清你付的 token 数，和你实际发的 token 数差多少。注入计费就藏在这个差里：中转在你的请求前拼接一段你看不见的长 prompt（有时是所谓的「系统优化提示词」），按总 token 向你收费。

## 对账方法

### 1. 本地计数

用本仓脚本数你发送文本的 token：

```bash
python3 scripts/token_count.py "你要发送的原文"
python3 scripts/token_count.py --file prompt.txt
cat prompt.txt | python3 scripts/token_count.py -
```

说明：
- 脚本优先用 tiktoken（`pip install tiktoken`）计数；没装时给出字符估算并明确标注「估算」，估算只看量级，不能用于 5% 级对账。
- 不同模型家族的 tokenizer 不完全一致：以 GPT 系分词数 Claude 文本（或反过来）会有系统性小偏差。所以对账看的是**比例与量级**：误差 <5% 视为正常，重点抓「多出几千」这种量级级异常。

### 2. 取控制台数字

发完同一条请求后，去中转控制台逐条用量里找到这条，记下：
- 输入（prompt）token 计费数
- 输出（completion）token 计费数
- 缓存相关字段（cache_creation / cache_read）如有，单独记，不混进输入总数里比

### 3. 算误差

```
误差率 = (计费输入 token − 本地计数) ÷ 本地计数 × 100%
```

取样要求：至少 3 条，覆盖短（几十字）、中（几百字）、长（数千字）三种长度，同一时段发完立刻对，别隔天找记录对错行。

## 判读标准

| 结果 | 判读 |
|---|---|
| 误差 <5%，且短长请求都如此 | 通过：计费口径正常 |
| 误差 5–10% | 黄旗：可能含合理的系统提示开销或分词差异，问客服要口径说明，并复测 |
| 误差 >10% | 红旗：超出分词差异可解释范围 |
| 每条都稳定多出一个近似固定的大数（如 +3000） | **注入计费实锤**：与文本长度无关的固定增量就是拼接 prompt 的长度 |
| 发 `hi` 也计费数千输入 token | **红旗**，与空请求测试互为印证（见 checklist 第 1 项） |

## 输出 token 的对账

输出无法预先计数（你不知道模型会生成多少），但可以验「回放一致性」：把控制台某条请求的输出原文复制下来本地计数，应与计费的输出 token 大致吻合（同样 <5–10% 口径）。输出对账偏差大，同样是问题。

## 注意事项

- 工具调用（function calling）、图片输入等场景的计费口径各家不同，对账时先用纯文本请求测，排除这些变量。
- Claude Code 等客户端自带系统提示：用客户端发请求时，本地只数你手输的那句话会对不上——这是客户端自己的 system prompt，不是中转注入。对账请用裸 API 请求（curl / 脚本）发，才能把变量控制住。这也是 `scripts/cache_probe.sh` 用裸请求的原因。
- 留证：对账异常时，请求原文、本地计数输出、控制台截图三样一起保留（密钥打码）。

## 自测通过标准

- 3 条不同长度请求的误差率都算出具体数字并记录
- 结论落到「通过 / 黄旗 / 红旗」之一，红旗时能指出是「比例型多扣」还是「固定增量型注入」
